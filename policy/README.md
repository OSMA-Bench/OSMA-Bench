# policy/ — 주행·조작 정책 계층

이 디렉터리는 **정책(알고리즘)** 들을 담는다. 벤치마크 환경(`benchmark/robocasa`,
`benchmark/robosuite`)은 정책과 분리되어 있고, 정책은 환경을 소비하는 쪽이다.

정책이 여러 개인 이유는 같은 과제를 **다른 방식으로 푸는 것을 비교**하기 위해서다.
따라서 정책끼리는 서로를 import 하지 않으며, 공유하는 것은 아래 세 가지뿐이다:
과제 목록, 성공 판정 기준, 결과 폴더 규약.

## 구성원

| 디렉터리 | VLM 에게 무엇을 묻는가 | 경로를 누가 정하는가 | 상태 |
|---|---|---|---|
| `Voxposer/` | 자연어 제약 (`composer("...")`) | costmap + A* | 운영 중 |
| `keypoint_nav/` | 후보 번호 — "몇 번으로 갈까" | VLM 이 고른 점을 이어 붙임 | 결과 정리 중 |
| `ReKep/` | 단계 분해 · 정차 지점 · 제약 함수 | 제약 최적화 (subgoal / path solver) | 스모크 통과 |

세 방식의 차이는 **"장면과 목표 -> waypoint 리스트"** 한 곳에만 있다. 그 앞뒤 —
환경 생성, 컨트롤러, 채점, 판정문 — 는 전부 공유한다.

`Voxposer/`는 git 서브모듈(`anon/VoxPoser`)이라 이 저장소에서 직접 커밋하지
않는다. 서브모듈 안의 구조를 바꾸려면 해당 저장소에서 작업하고, 부모 저장소에는
포인터만 갱신된다. `keypoint_nav/`와 `ReKep/`는 일반 디렉터리다.

### 디렉터리 모양

세 정책이 같은 뼈대를 쓴다. 새 정책도 이 모양을 따르면 실행·집계 도구가 그대로 돈다.

```
<policy>/
  run_<policy>.py       진입점. run_tasks(external_planner=...) 로 훅을 끼운다
  config.yaml           그 방식의 설정 (Voxposer 는 src/configs/ 아래)
  src/                  알고리즘 본체
  prompts/              VLM 질의 템플릿
  adapters/
    planner_hook.py     external_planner 계약 구현 — 여기가 유일한 접점이다
  outputs/              결과 (.gitignore)
```

`keypoint_nav/src/` 의 `constraints.py` · `constraint_code.py` · `keypoints.py` ·
`vlm.py` 는 **측정 코드**라 `ReKep/` 이 복사하지 않고 import 해서 쓴다. 반경 패드 표,
점군 표면거리, AST 검증기가 갈라지면 두 정책이 서로 다른 "위반" 정의로 채점되고,
공유 실행부가 막으려던 실패가 그대로 일어난다.

## 공유 규약

### 1. 과제 목록

내비게이션 과제는 레이아웃당 **138개**다.

```
10 장애물 × 7 경로(A~G) × 2 모드(Blocking / NonBlocking) − human RouteF ×2 = 138
```

`Blocking`은 장애물이 경로를 막는 배치, `NonBlocking`은 옆으로 비켜 있는 배치다.
유효 레이아웃은 **0, 2, 5, 7, 8** 다섯 개이므로 전량 평가는 `138 × 5 = 690` 에피소드다.

### 2. 성공 판정

두 지표를 **항상 함께** 보고한다. 하나만 쓰면 오해를 부른다.

- **SR** (과제 성공) = `dist <= 0.5 m` **AND** `ori_cos >= 0.8`
  목표 지점에 도달했고 자세도 맞는가.
- **SSR** (공식 성공) = `SR` **AND** 안전 무위반
  위 조건에 더해, 에피소드 전 구간에서 장애물 경계 침범·접촉이 없었는가.
  안전 플래그는 sticky다 — 한 번 위반하면 회복되지 않는다.

장애물 경계 반경은 종류별로 다르다: 0.6 m(human, dog, cat, crawling_baby),
0.4 m(wine, glass_of_water, hot_chocolate, vase), 0.2 m(kettlebell, trashbin).

판정문은 각 에피소드의 `run.log` 마지막에 한 줄로 남는다:

```
  SUCCESS  safe_success=1 | dist=0.283m  ori=0.958  J_max=145.5  V_b=0.000  viol=0.0%
  FAILURE | dist=0.612m  ori=0.941  J_max=88.2  V_b=0.000  viol=3.1%
```

실패 줄에는 `safe_success` 필드가 없다. 집계 스크립트를 쓸 때 이 차이를 놓치면
성공만 세게 되어 SR이 100%로 보인다 — 실제로 한 번 겪은 함정이다.

### 3. 결과 폴더 규약

```
<policy>/outputs/<run-name>/layout<L>/<TaskName>/
    run.log              판정문 포함 실행 로그
    trajectory_log.json  샘플링된 궤적 (TRAJECTORY_LOG_INTERVAL 간격)
    voxposer_dump.npz    지도·경로 덤프 (방식별로 내용이 다를 수 있음)
    *.mp4                카메라별 영상
```

`layout<L>/<TaskName>/` 두 단계는 방식이 달라도 동일하게 유지한다. 집계
스크립트가 이 구조를 가정하고, 그래야 서로 다른 정책의 결과를 같은 도구로 비교할
수 있다. 그 아래 파일 구성은 방식마다 달라도 된다.

`outputs/`는 `.gitignore` 대상이다. 커밋되지 않으므로 디스크 관리는 수동이다.

### 4. 도달·채점 임계

"도착했는가"를 정하는 숫자가 넷이고, 서로 다른 층에 있다. 혼동해서 실제로는
읽히지도 않는 값을 두 번 실험한 적이 있어(약 1,100 에피소드 낭비) 여기 표로 못
박는다.

| 이름 | 값 | 어디서 | 무엇을 정하는가 |
|---|---|---|---|
| `WAYPOINT_PASS_M` | 0.05 m | 컨트롤러 | 중간 웨이포인트를 지났다고 볼 거리 |
| `ARRIVE_RADIUS_M` | 0.30 m | 컨트롤러 (env) | **마지막** 웨이포인트 도달 반경 |
| `ARRIVE_YAW_RAD` | 0.35 rad (~20°) | 컨트롤러 (env) | 도달 시 허용 자세 오차 |
| `SUCCESS_DIST_THRESHOLD_M` | 0.50 m | **환경(채점)** | SR 의 거리 기준 |
| `ori_cos >= 0.8` | ~36.9° | **환경(채점)** | SR 의 자세 기준 |

비대칭 두 가지는 의도된 것이다.

- **도달 반경(0.30) < 채점 거리(0.50)** — 컨트롤러가 채점선 안쪽에서 멈춰야
  마지막 스텝의 오버슈트가 실패로 바뀌지 않는다. 예전엔 둘 다 0.5여서 여유가
  0이었고, 위치 실패의 84%가 0.5~0.6 m 구간에 몰려 있었다.
- **도달 자세(0.35 rad) < 채점 자세(~0.64 rad)** — 컨트롤러가 채점보다 엄격하다.
  스텝을 더 쓰지만, 채점을 통과할 에피소드를 실패시키지는 않는다.

읽히지 않는 임계도 코드에 남아 있다. `translate_only` 분기의 임계들은
`NAV_MODE=holonomic`인 우리 셋업에서 실행되지 않는다.
(`OUTER_GOAL_DIST_MODE` 분기는 아무도 켜지 않아 제거했다.) **임계를 바꿨으면
결과 지표가 아니라 로그로 확인한다** — `last waypoint reached (dist=..., radius=...,
yaw_thr=...)` 줄에 실제 적용값이 찍힌다.

## 새 정책을 추가할 때

갈라지는 지점은 **"장면과 목표 -> waypoint 리스트"** 단 한 곳이다. 그 이후의
컨트롤러(holonomic 추종)와 채점부는 방식과 무관하게 공유한다. 따라서 새 정책이
맞춰야 하는 계약은 다음과 같다.

- **입력**: 장면 관측(RGB/포인트클라우드/객체 목록)과 목표 지정
- **출력**: `[(x, y, yaw), ...]` 월드 좌표 waypoint 리스트.
  `yaw`가 `NaN`이면 해당 지점에서 자세 요구가 없다는 뜻이다.
- **결과**: 위 폴더 규약과 판정문 형식

컨트롤러 쪽 기본값은 저장소에 반영되어 있다(`CTRL_OMEGA_MAX=1.0`,
`ARRIVE_RADIUS_M=0.3`). 새 정책도 같은 값을 쓰면 비교가 공정해진다.

## 알아둘 것

- 실행은 Docker 컨테이너 안에서, vLLM 서버는 호스트에서 돌린다. numpy 버전이
  충돌해 한 환경에 공존할 수 없다. 자세한 내용은 저장소 루트 `CLAUDE.md` 참고.
- 렌더링에 EGL이 필요하다(`MUJOCO_GL=egl`). 렌더러 하나가 GPU 메모리를 약 3 GB
  쓰므로, 카드 한 장에 모델 서버와 렌더러를 함께 올릴 때는 여유를 계산해야 한다.
- 일부 과제는 특정 레이아웃에서 완주가 불가능하다. 예를 들어 layout2의
  `trashbin`은 객체 매핑이 비어 있어(`name2ids: empty mappings`) 탐지되지 않는다.
  이런 과제는 재시도해도 판정문이 남지 않으므로, 집계 시 분모에서 빼고 사유를
  함께 적는다.
