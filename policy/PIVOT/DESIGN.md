# PIVOT 방식 2D 네비게이션 정책

PIVOT(관계 키포인트 제약)의 **알고리즘 구조**를 이 벤치마크의 2D 주방 네비게이션으로
옮긴 것이다. 원본은 OmniGibson + 로봇 팔 6D 조작용이라 그대로 돌지 않는다.

핵심은 VoxPoser·keypoint_nav 와 무엇을 공유하고 무엇만 다른가다:

- **공유**: 환경 생성, 에피소드 루프, 컨트롤러, 평가, 판정문. `external_planner` 훅
  자리에 붙으므로 `run_tasks` 를 그대로 쓴다. 평가를 복제하면 임계가 조용히 어긋난다.
- **다른 것 하나**: VLM 에게 **경로를 묻지 않는다.** 단계 분해와 제약 함수만 받고
  경로는 solver 가 푼다. keypoint_nav 는 후보에 번호를 붙여 "몇 번으로 갈까" 를 묻는다.

## 구조

```
run_pivot.py            진입점
adapters/planner_hook.py  external_planner 구현
src/
  sdf.py       occupancy -> 부호거리장 + 보간기
  costs.py     충돌·일관성·경로길이·회전·불가능 비용
  subgoal_solver.py / path_solver.py
  interp.py    정규화·보간·경로길이·각도 wrap
  stages.py    단계 분해 질의 파싱·주입
  loop.py      가상 상태 반복 + backtracking
prompts/stage_decomposition.txt
```

`constraints.py`, `constraint_code.py`, `keypoints.py`, `vlm.py` 는 keypoint_nav 것을
**import 해서 쓴다(복사 금지)**. 반경 패드 표·점군 표면거리·AST 검증기는 측정 코드라,
복사본이 갈라지면 두 정책이 서로 다른 "위반" 정의로 채점된다.

## 원본과 다른 점

옮기면서 생긴 차이를 전부 여기 적는다. 적지 않으면 나중에 결과가 PIVOT 의 성질인지
우리 손질의 결과인지 가릴 수 없다.

### 1. 훅은 에피소드당 한 번만 불린다

`robocasa_config.yaml` 이 navigation 에 `max_plan_iter: 1` 을 준다. 따라서 PIVOT 의
"풀고 → 몇 스텝 실행 → 상태 재관측 → 다시 풀기" 루프를 시뮬레이터를 통해 닫을 수 없다.
그 루프를 **훅 안에서 가상 상태로** 돌린다. 구조는 같고 "상태 읽기" 만
`env.get_ee_pose()` 대신 마지막으로 내놓은 waypoint 가 된다.

`max_plan_iter` 를 늘려 해결하지 않는다 - 그것은 모든 정책이 공유하는 실행 경로를
바꾸는 것이고, "계획 단계만 갈아끼운다" 는 비교의 전제를 깬다.

부수 효과 하나는 원본보다 **깨끗하다**: 계획 시점에 로봇이 전혀 움직이지 않았으므로
backtracking 이 물리적 되돌아가기를 뜻하지 않는다. 버려진 구간을 로봇이 지나지 않는다.

### 2. 비용 항 대응

| PIVOT | 가중치 | 여기 |
|---|---|---|
| collision (SDF) | 0.8 / 0.5 | 그대로 |
| pose consistency | 1.0 | 그대로 |
| IK cost | 20.0 | **회전 비용** 으로 치환 |
| joint regularization | 0.2 | 드롭 |
| grasp metric | 10.0 | 드롭 |
| path length | 4.0 | 그대로 **단, 직선거리로 정규화**(3 참조) |
| 제약 위반 | 200.0 | 그대로 |
| — | — | **불가능 비용 5000.0 추가**(4 참조) |

홀로노믹 베이스는 자유공간이면 어디든 도달하므로 IK 의 "도달 가능한가" 가 아니라
"싸게 도달하는가" 가 대응한다. 회전 비용은 [0,1] 로 정규화한다.

### 3. 경로길이를 직선거리로 나눈다 — 작업공간 크기 보정

**가중치 변경이 아니라 스케일 보정이다.** PIVOT 은 0.55 m 작업공간이라 이 항이 0.3
수준이지만, 6 m 주방에서 그대로 두면 5~6 이 되어 충돌 항(0.5 × 침범 합)을 압도한다.

실측으로 확인한 증상: 계획 경로 41 점 중 **30 점이 장애물 안쪽**(최대 0.56 m 깊이)인
해가 최적으로 나왔다. 벽을 뚫고 직선으로 가는 쪽이 비용상 이득이었기 때문이다.
직선거리로 나눠 무차원화한 뒤 30 → 12 로 줄었다.

`opt_pos_step_size` 를 0.20 → 0.60 으로 다시 잡은 것과 같은 종류의 보정이다.

### 4. "불가능" 비용 — IK 도달불가의 네비게이션 대응

3 번만으로는 부족했다. 남은 관통의 원인은 **키포인트가 물체 중심**이라는 데 있다.
`sink`, `stove` 의 중심은 조리대 **안쪽**이다. VLM 이
`progress_cost(state, keypoints['sink'], 0.4)` 를 쓰면 가중치 200 이 subgoal 을 조리대
안으로 끌어당기고 충돌 항 0.8 은 상대가 되지 않는다.

이것은 조작과 네비게이션의 구조적 차이다. 팔은 물체 중심 **위로** 뻗을 수 있어 중심을
목표로 삼는 것이 말이 되지만, **바퀴 베이스는 그 자리에 있을 수 없다.** 그래서 베이스가
점유 셀 안에 있는 것은 비싼 것이 아니라 불가능한 것으로 다룬다 - PIVOT 에서 IK 비용이
하던 역할이다.

**어느 반경으로 불가능을 선언하는가**가 이 항의 전부다. 양쪽 다 실패한다:

- 로봇 반경(0.43 m)을 그대로 쓰면 - 이 맵은 보수적이라 로봇의 **출발 위치조차** 여유가
  0.06~0.22 m 인 곳이 있어, 출발점부터 불가능해져 solver 가 아무 데도 못 간다.
- 0 으로 두면(중심만 검사) - 관통은 없는데 최소 여유 0.06 m 짜리 경로가 나온다.
  몸통이 벽에 걸려 로봇이 물리적으로 지나가지 못한다. 실측: HumanBlockingRouteB 가
  계획상 `done` 이고 waypoint 간격도 정상인데 목표 1.43 m 앞에서 정지했다.

그래서 **출발 위치의 실제 여유**에서 반경을 정한다 (`min(로봇 반경, 출발 여유 − 0.02)`).
출발점이 증명한 만큼은 요구하되 그 이상은 요구하지 않는다. 값은 `infeasible_radius` 로
로그에 남긴다.

효과: 관통 **104/779 → 0/705 점**, 경로 최소 여유가 15/15 모두 **0.22 m 이상**
(중심만 검사할 때는 0.06 m 까지 내려갔다).

### 5. 단계 분해는 VLM 이 정하되 1~4 로 제한

PIVOT 은 과제 문장에서 단계를 뽑는다. 네비게이션에는 그런 분해가 없지만
**"무엇을 지나가는가" 가 곧 단계**다. 안전장치:

- 마지막 단계에 `progress_cost(GOAL)` 자동 주입. 없으면 아무것도 로봇을 목표로 당기지
  않아 일관성 1.0 과 경로길이 4.0 만 남고 subgoal 이 제자리에 주저앉는다. PIVOT 에서는
  과제 문장이 그 역할을 하므로 편법이 아니다.
- 중간 단계에 **항상** 약한 `progress_cost` 주입. 처음에는 "subgoal 이 비어 있을 때만"
  이었는데 부족했다 - VLM 이 쓴 `standoff_cost` 가 출발 시점에 이미 만족되면 비용이 0 이라
  전진을 만드는 힘이 없다. **만족된 제약과 "비어 있음" 은 solver 입장에서 구별되지 않는다.**
  실측: 앞 5 개 waypoint 가 로봇 위치와 동일해 로봇이 0.9 m 만 가고 멈췄다.
- 주입은 전부 `injected` 로 로그에 남긴다. 사후에 "VLM 이 쓴 것" 과 "우리가 채운 것" 을
  가르지 못하면 결과가 모델의 판단인지 우리 발판인지 알 수 없다.
- 함수 하나가 없는 이름을 가리켜도 나머지는 살린다(`_split_defs`). 전부 버리면 단계
  분해가 통째로 사라지고 우리 발판만 남는다.

### 6. path 제약은 한 점을 볼 때도 `Traj` 로 감싼다

path 제약은 `clearance_cost(traj, kp, margin)` 처럼 궤적을 받는 함수다. 3-튜플 pose 를
그대로 넘기면 매번 예외가 나고, 예외를 삼키는 코드가 그것을 가려 **기능이 이름만 남는다.**

두 곳에서 이 실수가 있었고 둘 다 조용히 실패했다:

- `loop._path_violation` - 되돌리기 판정. 위반이 늘 `-inf` 로 남아 **backtracking 이
  구조적으로 절대 발동하지 않았다.** 15/15 에서 `-inf` 였다. 진입 위반값을 로그에 남기고
  나서야 "제약이 늘 만족돼서 안 돈다" 와 갈렸다.
- `costs.subgoal_cost` - subgoal 을 풀 때 path 제약도 함께 보는 부분. 기여가 늘 0 이라
  PIVOT 의 그 성질이 작동하지 않았다.

`tests_r3.py` 의 시험용 제약이 pose 를 받도록 쓰여 있어 **시험이 버그를 인코딩하고**
있었다 - 시험은 통과하는데 실제로는 죽어 있었다. 시험을 실제 계약에 맞췄다.

고친 뒤: 진입 위반값이 실수로 나오고(중앙 -0.249, 최대 0.475) 30 회 중 8 회가
tolerance 를 넘으며, 되돌리기가 실제로 발동한다(15 건 중 4 건).

### 7. 루프가 일찍 끝나면 목표까지 한 구간 더 푼다

되돌리기가 살아나자 `backtrack_stuck` 으로 끝나는 에피소드가 생겼다. 종료 보장 장치가
동작한 것이므로 그 자체는 정상이지만, 그때 마지막 자세가 목표에서 멀다. 거기에 목표점을
**그냥 이어 붙이면 컨트롤러에게 순간이동인 한 구간**이 생긴다.

실측: 정상 에피소드의 waypoint 최대 간격은 0.11~0.30 m 인데, 끊긴 에피소드만 1.74 /
1.98 / 1.98 / 3.20 m 짜리 구간이 하나씩 있었고 **실패한 에피소드가 정확히 그것들이었다**
(도달 거리 0.86 / 1.54 / 3.71 m).

남은 거리가 한 걸음(0.35 m)보다 크면 path solver 로 마지막 구간을 푼다. 고친 뒤 최대
간격이 15/15 모두 0.30 m 이하가 되고 도달 거리도 전부 0.31 m 이내로 들어왔다.

### 8. 진행 방향 변화를 벌하는 항 (`smooth`, 4.0)

PIVOT 에는 대응이 없다 - 팔 경로는 짧아 경로길이 항만으로 충분히 곧게 펴진다.
우리는 두 가지가 겹쳐 **진행 방향을 벌하는 항이 하나도 없었다**:

- 경로길이를 직선거리로 나누면서(3 번) 지그재그를 억제하던 힘이 함께 약해졌고,
- `turn_cost` 는 홀로노믹 베이스의 **yaw** 를 보므로 공간적 지그재그를 전혀 잡지 않는다.

실측: 실패 에피소드의 계획 경로가 53 점 중 10 곳에서 20 도 이상 꺾이고 최대 158 도로
되돌아왔다. 컨트롤러 추종 편차가 평균 0.215 m 로 벌어졌다(정상 건은 0.03~0.07 m).
항을 넣은 뒤 편차 분포가 전반적으로 내려갔다(최대 0.215 → 0.192).

### 9. 도착 자세는 마지막 구간에 나눠 싣는다

도착 자세를 마지막 한 점에만 꽂으면, 접근 방향과 크게 다를 때 로봇이 그 자리에서
통째로 돌아야 한다. 실측: CatBlockingRouteB 에서 마지막 점 하나에 yaw 가 166 도 튀었고,
로봇이 도는 사이 목표를 **0.72 m 지나쳐** 실패했다.

마지막 1 m 구간에 선형으로 나눠 실어 접근하면서 돌게 한다. 도착 자세를 정하는 규칙
자체(`_goal_yaw`)는 keypoint_nav 와 같게 유지한다 - 그것이 다르면 판정이 갈린다.

### 10. `pace_cost` 는 solver 비용에 넣지 않는다

`Traj.v/a/j` 는 시간으로 나누는데 path solver 의 제어점은 시간이 아니라 거리 간격이라
속도가 무의미해진다. 기하만 푸는 최적화기에 시간 미분 제약을 넣으면 **비용은 내려가는데
아무것도 재지 않는** 일이 된다. 속도는 keypoint_nav 처럼 `_pace_profile` 로 따로 다룬다
(이 정책은 속도를 정하지 않으므로 `None` 을 넣는다).

### 11. SDF `fill_value` 는 반드시 음수

PIVOT 은 0 을 쓰지만, 0 이면 최적화기가 "맵 밖은 공짜" 임을 발견해 subgoal 을 주방 밖에
세운다.

## 아직 답하지 못한 것

- **단계 수가 거의 항상 3 이다.** 프롬프트가 phase 예시를 셋 나열하던 것이 3 을
  암시하는 앵커였다 - 예시를 하나로 줄이고 출력 예시의 `# 1:` / `# 2:` 도 지웠더니
  1 단계 답이 나오기 시작했다(30 건 연속 3 → 15 건 중 1 건이 1). 여전히 3 이 압도적이라
  앵커가 완전히 빠졌는지, 이 장면들이 실제로 3 단계인지는 가르지 못했다.
- 되돌리기는 발동하는 것이 확인됐지만(중간 실행에서 15 건 중 4 건), 여유가 올라간 뒤
  최종 실행에서는 0 회다. 제약이 진입 시점에 늘 만족되기 때문으로 보이나 확인하지 않았다.
- **안전 위반은 이 문서가 다루지 않는다.** 여기 실린 것은 전부 "계획이 나오고 로봇이
  목표에 닿는가" 다. 생물 티어(0.6 m) 위반은 두 정책이 공유하는 별도 문제다.
